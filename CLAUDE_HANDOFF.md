## 1. Product purpose and core concepts

**ManagR** is the operating system PG/hostel (paying-guest / hostel) owners use to run
their business — properties, rooms/beds, tenants, leads, visits, bookings, payments.

The **ManagR Website Builder** ("the Website workspace") is a constrained no-code layer
*inside* ManagR that turns data the owner already keeps into a public website on a
permanent web address, without ever letting the owner break the site, expose a tenant, or
contradict live operational data.

**Core positioning (📐 settled, load-bearing for every future decision):**
> "Presentation is editable; truth comes from ManagR." Every value a section can show is
> exactly one of two things: owner-editable copy/arrangement, or a live read-only binding
> to ManagR data (rent, room types, amenities, availability, approval status, address).
> The builder never writes operational data.

**Users** (from `PRODUCT.md`):
- **Owner** (primary) — runs 1–40 properties, often not comfortable with computers,
  frequently mobile-first (a five-year-old Android, standing in a corridor). Wants one
  link for WhatsApp/Instagram/visiting card/board that looks like a real business.
- **Owner's staff** (managers/wardens) — view-only in the builder; their daily bed-status
  entry in ManagR is what keeps public availability honest.
- **Visitor** (the audience the site is *for*) — students/professionals/parents, almost
  entirely mobile, slow connection. Want, in order: photos, rent, location, "is it free
  now", how to call. "Direct from owner, no brokerage" is a real trust signal.

**Two plans** (📐 settled): `basic` (free) and `advanced` (paid). Plan states:
`basic · trial · advanced · expiring · payment_failed · lapsed`. On lapse the site
**quietly falls back to the Basic look** — Advanced sections auto-hidden (never deleted),
nothing is ever deleted. See `PRODUCT.md` for the full capability matrix.

Full product/IA detail lives in `BUILDER-PRODUCT-ARCHITECTURE.md` and `PRODUCT.md` —
**read those before making any product-shape decision**; this file summarizes, it does
not replace them.

## 6. Design system and reusable components

**Single source of truth:** `src/styles/globals.css`'s `:root` block. Every color, radius,
shadow, and easing value lives there as a CSS custom property, mapped into
`tailwind.config.ts` theme keys. **To retheme the whole product, edit `:root` — never a
raw hex value in a component.**

**Surface ladder** (this is what gives the UI depth, not shadows):
`--background #fafafa` (app) → `--workspace #ecedf0` (editor canvas) → `--surface #fff`
(panels/cards) → `--surface-2 #f7f8f9` (quiet grouping) → `--sunken #f1f2f4` (wells/tracks).

**Radius hierarchy — 5 / 8 / 10 / 14 / pill:** 5 = checkbox·kbd, 8 = icon buttons·
segmented·chips, 10 = buttons·inputs·rows, 14 = cards·panels·modals·website frame,
pill = status only.

**Status colors** each have `DEFAULT` / `-foreground` / `-surface` / `-border` tokens:
`success`, `warning` (+ `-wash`), `advanced`, and now `destructive` (this session added
`--destructive-border`, previously the only status color missing one — see §14).

**Buttons** (`components/ui/button.tsx`): one CVA system. Sizes `xs/sm/default/lg` +
`icon`/`icon-sm`. Variants: `primary` (coral, white text always) · `navy` · `blue` ·
`secondary` · `outline` · `ghost` · `destructive` · `link`, plus a `loading` prop.

**Cross-screen primitives** live in `src/components/common/index.tsx` — this is the file
to fix a pattern in, not a screen:
- `PageHead`, `SectionHeader`, `PanelHeader`, `Notice`/`Callout` (alias), `EmptyState`,
  `ChoiceRow`/`ChoiceGroup` (border-only selection language — no fill, see §7), `StatusBadge`
  (dot+text, or `pill`), `MetricCard`, `IconTile` (tinted rounded icon square, 6 tints),
  `CardHead` (icon tile + bold title + grey subtitle + right action, single-line-truncated
  — used only by `WebsiteHome`'s "Your website" card; distinct from `SettingsCard`),
  `FromManagR`, `BoundField`, `AdvancedLock`.
- **`Page`** (the ONE content-frame component for management pages) — `size` prop:
  `"content"` (`max-w-[840px]`, default) / `"wide"` (`max-w-[1040px]`) / `"full"`
  (`max-w-none`). **Deliberately has no `mx-auto`** — left-anchored to the shell's own
  padding so every page shares an identical left edge regardless of size. (Added this
  session, §14 — replaces an earlier single-fixed-width version.)
- `PageBody` (the `space-y-5` rhythm under `PageHead`).
- **`SettingsCard`** — icon-tile + bold title + grey description header / `space-y-4`
  content / optional `surface-2` footer. **This is the "icon-in-square + heading +
  subheading" pattern used by Settings, Health, Plan, Analytics, and several cards on
  Availability/Visits/Enquiries/Bookings.** Its header spacing/icon-alignment was tightened
  this session (§14) — this is the correct place to adjust that pattern again, never per-card.
- `Field` (vertical label/control/hint), `ToggleField` + `FieldGroup` (borderless labelled
  switch/checkbox rows, dividers, never boxes), `Segmented` (small either/or choices),
  `ListContainer` (the one operational list — desktop rows / mobile cards), `FilterBar`,
  `SaveBar` + `useSaveState` (sticky save-state bar: `clean → dirty → saving → saved`,
  appears only when there's something to save).

**Editor-only visual grammar** — `src/features/editor/panel.tsx`: `Panel`/`PanelHeader`/
`PanelScroll`/`PanelFooter`, `Group` (collapsible band), `Row`, `Field`, `Seg`/`SegToggles`,
`ChoiceGrid`/`ChoiceCard`/`LayoutMini`, `ScopeChip`. This is a **separate** component
family from `src/components/common` — do not merge them; they serve different visual
contexts (editor chrome vs. management pages) by design.

## 7. Important design decisions that are already settled (📐 do not reverse)

1. **Presentation is editable; truth comes from ManagR.** Never let a section write
   operational data. Never invent a way for the builder to override live availability,
   pricing, or approval status.
2. **One selection language for choice-style controls: a border, nothing else** (see
   `ChoiceRow` in `common/index.tsx`). No filled/tinted selected background on that
   specific pattern — this was a deliberate simplification versus an earlier
   checkmark-on-circle approach (see §10, rejected approaches).
3. **`Page` has no `mx-auto`.** Every management page is left-anchored to the shell's own
   padding, not centered independently. This is what keeps every page's left edge
   identical regardless of its `size`.
4. **Card-header pattern (`SettingsCard`) belongs to one shared component.** Never
   hand-roll a new icon+title+subtitle header on a page; extend `SettingsCard` (or
   `CardHead` for the one legitimately different single-line pattern on WebsiteHome).
5. **Design popup ("Design") is a single continuous scroll popup — Style → Brand →
   Typography — with no dots, no side rail, no tabs.** See §11 in full; this was a
   deliberate rejection of two alternative directions (split-preview, bottom-sheet grid)
   that are preserved for reference in `/design-lab` but are **not** the production design.
6. **The editor is desktop-only for editing; tablet/phone show a fixed "Editing is
   available on desktop" notice with a Preview CTA.** See §8. This is a real product
   decision, not a missing responsive implementation.
7. **`SectionMeta.structural` sections (header, footer) can never be removed or reordered
   past their fixed position.** Header always first, footer always last.
8. **Colors, fonts, and corner radius are global (Design panel) — never per-section.**
   Section-level customization is limited to layout variant, spacing (cosy/compact/roomy),
   per-screen visibility, and content fields — see `WEBSITE-SECTION-CONTRACTS.md`'s
   "Controls every section shares" table.
9. **Version Restore and Preview are real** — each `PublishVersion` carries a full
   `SiteSnapshot`; restore loads it as the draft, preview renders the visitor site from it.
   Not a stub.
10. **Two plans, six plan states**, and lapse is **graceful** — Advanced sections
    auto-hide, nothing is deleted, branding reverts to Basic look. Never design a "lose
    your data" lapse experience.
11. **A recurring CSS bug pattern is now understood project-wide** (see §14): a Tailwind
    opacity modifier (`/NN` or `/[0.NN]`) silently resolves to nothing when applied to a
    color whose CSS custom property is a plain hex string (`--brand`, `--destructive`)
    rather than an RGB channel triplet. **Never write `bg-brand/NN`, `border-destructive/NN`,
    etc.** Use the precomputed solid tokens instead (`-surface`, `-border`, `bg-tint-coral`,
    etc.), or a format-agnostic utility like `brightness-90` for a one-off hover darken.
    If you need a new tint, add a real token in `globals.css`/`tailwind.config.ts` rather
    than reaching for an opacity modifier on an existing hex var.

## 8. Website editor architecture and behavior

**Full-screen, no `ManagRShell`.** `EditorScreen.tsx` renders `fixed inset-0` with its own
toolbar/canvas/inspector grid — it deliberately does not share the app chrome.

**Structure** (desktop, `lg:` and up):
```
EditorToolbar (EditorChrome.tsx)
┌───────────────┬─────────────────────────┬───────────────────┐
│  LeftPanel     │      WebsiteCanvas       │   InspectorPanel  │
│  (Layers/      │  device-framed live      │   Content/Layout/ │
│   Pages/Add/   │  draft preview           │   Visibility/Data │
│   Assets)      │                          │                   │
└───────────────┴─────────────────────────┴───────────────────┘
```
Grid columns: `lg:grid-cols-[284px_1fr_324px]`, `xl:grid-cols-[300px_1fr_340px]`.

**📐 Desktop-only editing (`EDITOR_MIN_WIDTH = 1024`, tied to the `lg` Tailwind
breakpoint) — settled, do not revisit:**
- Below `lg`, the *entire* three-column editor is swapped (via CSS visibility, not
  unmounting) for a fixed notice: "Editing is available on desktop" + a "Preview website"
  button linking to `/website/preview`.
- **Both the desktop editor and the notice are always mounted; only CSS decides which
  shows.** This means resizing the window never remounts anything and never touches the
  store — draft edits, selection, undo history, and current page all survive a resize in
  either direction for free. Do not "fix" this by conditionally rendering one or the other
  in JS — that was a deliberate choice to preserve state across a resize.
- This rule is **unrelated** to the Desktop/Tablet/Mobile device switcher inside the
  editor, which controls what the *website being edited* is previewed at — not whether the
  editor itself can run.
- **This entire area (its layout, responsive strategy, and copy) is explicitly out of
  scope for the general Website-workspace refinement work done this session.** It has not
  been touched by any of that work.

**Overlay system** (`EditorContext.tsx`) — one `overlay` union state: `null | "publish" |
"versions" | "design" | "command" | "responsive" | "pagePick" | "editorMore" |
"mobileSection" | "mobileLayers" | "mobileAdd"`. Desktop overlays are centered `Dialog`s;
`Sheet`s are reserved for genuinely mobile-only surfaces (`EditorMore`,
`MobileLayers`/`Add`/`Section`).

**Keyboard shortcuts** (in `EditorScreen.tsx`): `Esc` closes overlay, `⌘/Ctrl+K` opens
Command menu, `⌘/Ctrl+Z` / `+Shift+Z` undo/redo, `⌘/Ctrl+Enter` opens Publish, `P` toggles
edit mode (guarded against firing while typing in a field), `Backspace` removes the
selected block (also guarded).

**Locked view** — a role without edit permission (`canEdit(s)` false) sees `EditorLocked`
instead of the editor: a centered card explaining the role restriction, with Preview/Back
actions. This is a real, implemented gate, not a placeholder.

## 10. Approaches tried and rejected (❌ do not reintroduce without being asked)

1. **Design popup: Split Preview and Bottom Sheet/Grid directions** — explored in
   `/design-lab`, not chosen. Continuous Sheet won (§11).
2. **Design popup "Style" as a curated visual-theme picker** (three named themes: "Clean
   Modern" / "Warm Family-run" / "Premium Co-living").
   **Rejected and corrected mid-session** — this conflated two different features. "Style"
   in the Design popup is now **spacing/density** only (`layoutDensity`: Compact/Balanced/
   Airy), confirmed with the product owner. The underlying `theme` field on `BuilderState`
   still exists and is untouched in the store, it simply has **no control surface in
   Design any more** — that's a product decision, not an oversight. See
   `DesignSheet.tsx`'s header comment for the full rationale.
3. **Circular color swatches with a checkmark icon for the selected brand color** —
   replaced with square swatches using the same `border-brand` selection language as every
   other card in the sheet, removing the one decorative icon that existed in the popup and
   the one exception to the "border-only selection" rule.
4. **Bare colored text acting as an implicit button** (e.g., "Custom colour" /
   "Reset to style colour" / "Website settings" pointer) — replaced with real `Button`
   components throughout the Design popup, because unstyled clickable text was being
   mistaken for a caption.
5. **Opacity-modifier Tailwind classes on hex-format CSS custom properties**
   (`bg-brand/[0.06]`, `border-destructive/25`, etc.) — not a "direction" so much as a
   recurring implementation mistake, but worth flagging as a pattern to never reproduce:
   found and fixed **repeatedly** across this session (Settings, Notice, StatusBadge,
   Button's destructive variant, WebsiteHome's "Next" banner, PlanBanner, Visits time
   chips). See §14 and §7.11. If you see this pattern anywhere else in the codebase, it is
   a bug, not a stylistic choice — fix it the same way (a precomputed solid token).

## 11. Design popup ("Design") — Continuous Sheet direction and its settled decisions

The production Design popup is `src/features/editor/overlays/DesignSheet.tsx`, opened via
`EditorContext`'s `overlay: "design"` state (triggered from the editor toolbar / command
menu). It is a single `Dialog`, one scroll area, three chapters in fixed order:

**Style → Brand → Typography** — no dots, no side rail, no tabs. This structure is
final and should not be changed without a new, explicit design decision (it already went
through two rejected alternatives, §10).

- **Style** — three equally-weighted cards (Compact / Balanced / Airy), each showing a
  `DensitySchematic` (three bars, gap proportioned from the *real* padding values
  `WebsiteCanvas.tsx` applies per density) — the preview never promises rhythm the site
  doesn't actually use. Drives `layoutDensity`.
- **Brand** — two distinct groups: **Logo** (a true square identity container + a real
  "Upload logo" `Button`, with the Website-settings pointer folded into a quiet info strip,
  not floating text) and **Brand colour** (square swatches, `border-brand` selected state,
  a "Custom colour" `Button` that reveals a hex `Input` + Apply `Button`, hex validated
  against `/^#([0-9a-f]{3}|[0-9a-f]{6})$/i`). Drives `brandColor`.
- **Typography** — a list of curated font-pair "personalities" (`FONT_PAIRS` in
  `data/managr.ts`), each with a compact specimen (heading + one line + a button styled to
  that pair's radius convention) — deliberately small, "sized to be scanned, not to
  simulate a website." Drives `fontPair`.

**Gating:** on Basic plan, the entire popup body is replaced by `AdvancedLock` — design
customization is an Advanced-only capability.

**Zero decorative icons in this popup by design** — the only icon that used to exist here
(a checkmark on a round swatch) was removed when swatches became square borders-only
(§10.3).

## 15. Interactions, state management, autosave/undo/redo

**State** — one `BuilderProvider` (`src/store/`), exposed via `useS()` (read state),
`useDispatch()` (write), `useDerived()` (memoized selector bundle: `advActive`, `url`,
`publicProperties`, `check`, `dirty`, …), and `useBuilder()` (adds `undo`/`redo`/
`canUndo`/`canRedo`).

**Autosave + undo (✅ implemented, real, not simulated-looking-real):**
- `CONTENT_ACTIONS` (a fixed `Set` in `reducer.ts`: `addBlock`, `removeBlock`, `moveBlock`,
  `reorderBlock`, `hideBlock`, `dupBlock`, `updateBlockData`, `blockLayout`, `blockDense`,
  `blockVisibility`, `setTheme`, `setDesign`, `setHeader`, `setFooter`, `applyTemplate`,
  `addPage`, `pageAction`, `restoreVersion`) are the actions that count as "content
  changed" — anything in this set pushes a `SiteSnapshot` onto a 50-deep undo stack
  (`history.current` in `BuilderProvider`) and flips `saveState`: `saving` immediately,
  then `saved` after a 550ms simulated-latency `setTimeout`.
- Undo/redo replay snapshots via `restoreSnapshot`, which re-applies `{pages, theme,
  brandColor, fontPair, shape, layoutDensity, globals}` — **not** the whole `BuilderState**
  (UI-only fields like `selection`/`leftMode`/`device` are untouched by undo, intentionally).
- **Persistence:** the entire `BuilderState` is serialized to `localStorage` under the key
  `managr_builder_react_v1` on every state change (`BuilderProvider`'s effect). A fresh
  session picks this up via `load()`, merged over `createInitialState()` so new fields
  added later still get sane defaults for old saved state.
- **Publish state machine:** `publishPhase: idle → publishing → success | error`, driven
  by `PublishDialog`. On success, a `PublishVersion` (with a full `SiteSnapshot`) is
  prepended to `state.versions` (capped at 12) and `state.published` is updated — this is
  what makes Version History's Restore/Preview genuinely load real prior content, not a
  placeholder.

**Keyboard interactions** are centralized in `EditorScreen.tsx` (§8) — do not duplicate
keyboard handling in child components.
